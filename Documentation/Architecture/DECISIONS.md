# Decisions

## Early decisions (D-1 to D-11)

Taken before the first version of the checklist viewer was built, where the architecture document and the plan left something open or disagreed. One line each; the later decisions below continue the numbering from D-12.

- D-1: **`ARCHITECTURE.md` overrides the plan on every conflict** (Bloc/Cubit, not `provider`; layered folders, not a flat layout; `ChecklistDocument`, not `ParseResult`; fixtures in `testing/fixtures/`; state keyed by name, not index). The plan only fills gaps: parser rules, UI details, acceptance criteria.
- D-2: Check state is keyed by **checklist name**. The parser therefore makes names unique: a duplicate becomes `Name (2)` with a warning. Two checklists with the same name would otherwise share check marks.
- D-3: `package:equatable` is allowed in `domain/`. The architecture says "Dart core only" but also lists equatable for models; it is pure Dart, so the layer script allows it.
- D-4: **No in-app "Load sample" button.** There is one `ChecklistSourceService` seam. The bundled sample was a second implementation of that seam, chosen in the development wiring, and `ChecklistRepository` stayed as the architecture sketches it. (Both the file source and the sample are gone; see D-69.)
- D-5: The **parse-warnings banner lives on the checklist list screen**, because a successful load navigates straight to the list.
- D-6: A document with **zero checklists** is an error from the repository (`ParseFailure`), not an empty success, so the home screen can show a clear message.
- D-7: `ChecklistProgressRepository` has `resetAll()`, and `HomeCubit` calls it after every successful load, so check marks from the previous file do not leak into the next.
- D-8: Latin-1 fallback decoding lives in `lib/utils/text_decoding.dart` (pure Dart), shared by every source of checklist text.
- D-9: Tests of temporary code lived under `test/**/temporary/`, so deleting the temporary code deleted its tests too. (Done; the isolation gate now fails if a `temporary/` folder returns.)
- D-10: `ChecklistDocument` carries `sourceName` (the name to display for where the checklist came from).
- D-11: Parse edge policies the plan left open: an empty checklist name becomes `Untitled checklist N` plus a warning; an empty `sw_itemvoid` is skipped with a warning; the result is the text after the first `|` up to the next `:` (so `A|B|C` gives the result `B|C`).

## Optional check-state persistence

Date: 2026-10-22. Decision: **no, defer** (the optional persistence is not built in the first version).

Reason: the first version is complete and meets all six acceptance criteria without it. Check marks reset when the app restarts, which is acceptable for a hand-ticked checklist. The seam is already in place (`ChecklistProgressRepository` with a future `services/local/` implementation), so adding it later changes no UI or domain code. `shared_preferences` is planned anyway, and persistence is better designed together with auto-check, which writes to the same repository.

## Check-state persistence revisited

Date: 2026-10-23. Decision: **yes, build it**; supersedes the deferral above.

Reason: if the app is killed mid-flight the pilot must not lose their place. Restore rule and storage are in `ARCHITECTURE.md` section 16.

- D-83 (2026-11-16, the user): **Lookup tables and calculated values: `sw_table`, `sw_row`, `sw_table_end`, `sw_calculate` (`GRAMMAR.md` section 5c).** A checklist file can carry a table of numbers (the first use: the maximum cruise power chart of the PC-12) and an item can show a value from it for the aircraft's state now. The user's design: `sw_table` names the table and its columns, `sw_row` holds the data, `sw_table_end` ends it, the block goes at the end of the file and is never shown, and `sw_calculate:table|column` shows one value. Built on that: the input columns are bound to a dataref or an expression of datarefs (so the ISA deviation, which has no dataref, is `OAT - (15 - 0.00198 * pressure altitude)`; the expression reuses the condition parser), the output columns are plain names, the rows must be a complete grid, and `sw_calculate` takes an optional label, unit and rounding step. The table is data in the user's own file, so nothing payware is shipped in the repository. Weight is in kg. The value is **live, not frozen** (nothing is stored in the progress file), and there is **no auto-check** from it for now. An input column may carry a label and a unit (`alt(Altitude, ft)=...`) for the messages; the display is one band under the item, with a warning first that names every input beyond the table (`GRAMMAR.md` L10); the calculated lines are not items. A `sw_item_heading` may carry `sw_calculate` lines too (2026-11-17, the user), so one item can show a second set of values under a heading, such as long range next to maximum cruise. Built in steps: the grammar, the model and the parser first; then the interpolation and the live subscriptions; then the line on the item; then the PC-12 file. The value is a multilinear interpolation of the rows around the inputs; an input beyond the table is held at the edge and flagged, an input with no value gives no value (N4), and the shown number is rounded to the line's step (`GRAMMAR.md` L7 to L9). The inputs are watched through `signalsFor` while the checklist is open and the values reach the rows through the detail cubit, which emits again only when a rounded value changes.
- D-84 (2026-11-17, the user): **Voice: the app reads the items aloud and listens for the answers. The marker is a block, `sw_challenge: ON` to `sw_challenge: OFF` (`GRAMMAR.md` section 5d).** The role of voice is the second pilot. A **challenge-response checklist** is for two crew: one reads the item aloud, the other checks it and answers. A **flow** (procedure) is done by one pilot from memory or from the list. The Thranda PC-12 file is mostly flows. Both use the same file syntax; the rows between `sw_challenge: ON` and `sw_challenge: OFF` are challenge rows and every other row is a flow row, so one checklist can mix them. **Flow rows:** voice reads the next unticked item and waits for the pilot to do it. The item is done when its dataref changes to the wanted state (auto mode only), when the pilot ticks it, or when the pilot says an answer. **Challenge rows:** voice plays the reading crew member. With auto on and one or two auto-checkable items in a row it says both parts, the challenge, a pause, then the response. With more than two in a row it says how many are verified, then reads the first unticked one and waits for the dataref or the pilot. With every row manual it reads one item at a time. With auto off a true dataref does not advance the list; only a tick or a spoken answer does. **Rules for both:** if the pilot's tick or spoken answer disagrees with the dataref, voice says "Double check <item name>" (this is the existing disagree state, not overridden). Saying "skip" skips the item (the amber skip). Spoken answers are the fixed words `check`, `set`, `on`, `off`, `closed`, and the item's own result text; a close but not exact match is answered with "Did you mean <answer>?" and the pilot says yes or no. **Pause:** the spoken command `pause checklist` and a Pause button stop the voice and flash PAUSED on screen (an icon and text, not colour alone); `resume checklist` or `continue checklist` (or a similar word before `checklist`) carries on. Headings, notes, details, calculated bands and items hidden by a switch are not spoken. **Settings:** two toggles, Voice for flows and Voice for challenges, both **off by default**. Voice never writes a dataref and ticks only what the pilot did or said. **Packages:** `flutter_tts` for speech out and `speech_to_text` for speech in, used only in `data/services/voice/` and wired from `config/`; `domain/` and the cubits never name them. **Platforms:** Android is the main target. Windows is **best effort**: it is kept because it is available and helps automated testing, and a cockpit PC or a second PC is a small group of users, so a Windows problem is written down in `BUILDING.md` and not worked around. iOS and macOS stay deferred. Built in steps: this decision with the grammar, plan and architecture changes; a short spike on the PC to see what `speech_to_text` does on Windows and offline (before any voice code); the parser; a pure prompt use case; the speech service and repository with a fake; the cubit; the settings and the Pause button; tests. The acceptance criteria are listed as planned in `PLAN.md` section 16 and get their numbers and tests step by step. Not run: the real checker on a file with `sw_challenge` (the plugin is assumed to warn about the unknown keyword and skip the line, so the items show as plain rows). **Matching (2026-11-17, built):** a spoken phrase is lower-cased and stripped of punctuation; a near miss is a close match when it is within 1 edit of a phrase of up to five letters or 2 of a longer one, and the phrase and the phrase heard are both at least three letters (so `on`, `off` and `no` must be exact). The resume words before `checklist` are `resume`, `continue`, `unpause` and `start`; the pause words are `pause`, `hold` and `stop`. A bare `continue` or `pause` is not a command, so talk in the cockpit does not stop the list. **Amended (2026-11-17, the user, after the first run on a phone):** the voice reads an item by its label only and waits for the action; after the action it says the result as the confirmation (a flow row; for a challenge row the pilot says the result). A challenge checklist's spoken title drops the word "challenge" and ends with "checklist" ("CHALLENGE BEFORE START" is "before start checklist"; the title on screen is unchanged). In auto mode, opening a checklist whose first open row is a challenge row (with the challenge voice on) makes the voice ask "Ready for <title>?" and wait for a yes (also ready, okay, roger, proceed, go ahead) or a tick by hand; auto-check ticking items does not start it, and manual mode does not ask.

- D-86 (2026-11-18, the user): **MSFS: how an unknown variable name is handled. Agreed design, nothing built yet.** Measured with a throwaway SimConnect probe (`Documentation/temp/`, not committed) against MSFS 2024 with the SWS PC-12; the probe built with the 2020 SDK connected to it. (1) An unknown **A-variable** (and a wrong unit) is refused by SimConnect with exception 7 `NAME_UNRECOGNIZED` right after the definition is sent, then 3 `UNRECOGNIZED_ID` on the request; the companion maps this to `unknown_name`, and since the exception arrives after the call it answers `subscribed` or `unknown_name` only once it has seen it or the next tick has passed (`PROTOCOL.md` section 7 already allows `subscribed` after the next tick). (2) A **B-variable** (input event) is checked against the list the sim returns for the loaded aircraft (`SimConnect_EnumerateInputEvents`: 196 entries in one packet for the PC-12); a name not on it is `unknown_name`. (3) An **L-variable** that does not exist is read as `0` with no error and no way to tell (`L:FSA_PROBE_DOES_NOT_EXIST` and a one-character typo both read 0), so the companion cannot report it. L-variable names are **case-insensitive** (the lower-case name followed the real switch); the companion treats names that differ only in case as one variable, and the case of A and B names has not been tested. - D-88 (2026-11-18, the user): **MSFS: how the companion detects an aircraft change, and the branch decision. Measured on MSFS 2024 with the PC-12 and the C152; the companion is not built.** (1) **Signals.** A load is `SimStop`, then `FlightLoaded` (a flight reload), then `SimStart` about 0.7 s later, then `AircraftLoaded` about 2 to 3 s after that; the event carries the path of the `aircraft.cfg`. `TITLE` and `ATC MODEL` already show the new aircraft before `AircraftLoaded`. Polling `TITLE` alone misses a reload of the same aircraft (two PC-12 reloads produced no change), so detection is driven by `SimStop` and `AircraftLoaded`. (2) **Rules.** On `SimStop` the aircraft is unavailable and nothing is reported; on `AircraftLoaded` the companion re-reads `ATC MODEL` and `TITLE`, clears its cached values and raises `generation`. Values are held back for a settle time after `AircraftLoaded` (start at about 2 s, to be measured): the first probe read garbage during loads (altitude 53819.6, parking brake 0, alternator 1). (3) **Pause.** Data keeps arriving at the normal rate while the sim is paused, so pause needs no special handling. (4) **Aircraft key.** A livery change changes only `TITLE`; `ATC MODEL` stays `PC12`. Default aircraft report a localisation key (`ATCCOM.AC_MODEL C152.0.text`, also seen for the C185), so the key is the token after `ATCCOM.AC_MODEL ` when that form is present, otherwise `ATC MODEL` as is. (5) **Input events.** `B:` names fail with `GET_INPUT_EVENT_FAILED` (42) on an aircraft that lacks them, and with error 1 during a load; the companion treats both as unavailable and retries on a back-off, not every tick (the probe flooded its log). L-vars of another aircraft read 0 without an error, so "wrong aircraft" is decided from the key, not from the values. (6) **Not measured.** How long the values stay wrong after `AircraftLoaded`; a stay on the main menu (the test only reloaded flights); a livery change inside a flight (seen only in the earlier probe, where `TITLE` changed with the same garbage values). (7) **Licence.** The SDK EULA (11/2019) permits our use (add-ons and plugins) and bans sharing the SDK "except for any distributable code"; the readable text does not define that term or name `SimConnect.lib`. Never commit SDK files; the companion builds against a local SDK; whether a release binary may contain the static library is still to be confirmed from clause 2 of the PDF or with Microsoft.
